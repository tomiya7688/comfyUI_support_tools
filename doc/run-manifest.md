# Cross-application run manifest

`shared.contracts.run_manifest` defines a versioned immutable record for execution identity and Job ID, lifecycle, input/output references, resolved settings, seeds and actual random selections, component versions, environment, warnings/errors, candidate decisions, repair/retry lineage, user overrides, and reproducibility level. Artifact contents stay outside the manifest; each reference can carry size, optional bounded SHA-256, and media timing fields such as requested/actual timestamp, PTS, and time base.

Use `create_run_manifest_for_job` to bind an existing `JobSnapshot` to explicit run metadata, save it, then persist the returned path through `JobRuntime.set_manifest_ref`. Applications without a Job can call `create_run_manifest`; all callers use `finish_run_manifest` for terminal status and outcomes. `generate_random_seed` records an explicit seed chosen by the application; non-random work need not invent one. `JsonRunManifestStore` writes atomic digest-checked JSON documents. `JsonLineRunEventStore` appends ordered lifecycle/progress records for one writer per run. The `RunManifestStore` protocol allows a project DB or index adapter without changing the schema.

Privacy is selected per field with `full`, `hash`, `summary`, or `none`. Keys such as `settings.prompt` can be removed while other settings remain replayable; hash/summary/none settings block replay. Unspecified fields default to full, so callers must mark prompts, paths, personal data, and large workflow payloads according to their data policy. No large intermediate data is embedded automatically. Artifact hashing is bounded and rejects files that change while being read.

`manifest_replay_request` returns saved inputs/settings/seeds only when settings are available in full. It describes a request and does not claim bit-exact output: `deterministic`, `best_effort`, and `non_deterministic` remain explicit. `compare_run_manifests` returns field-level differences. Common CLI registration provides `run show`, `run replay`, and `run compare` commands for later CLI harness integration. Schema v0/v1 payloads migrate additively to v2 with a Job ID field; unknown future versions are rejected.
