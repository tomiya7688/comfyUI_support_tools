# コーディング規約

[日本語](コーディング規約.md) | [English](coding-standards.md)

本規約は comfyUI_support_tools 全体で使用する一般コーディング規約です。

このプロジェクトの標準設計は、**UPD + パーツ組み換え設計（Part Swap Design）** とします。

- UPD は、責務を UI / Process / Data のどこへ置き、要求・結果をどの境界で受け渡すかを定義します。
- パーツ組み換え設計は、どこまでを1つの交換可能なパーツとして閉じ、呼び出し元を内部実装ではなく安定した入出力契約へ依存させるかを定義します。
- Message Orientated Design は、独立して状態を所有する主体同士を、直接の内部関数呼び出しや状態参照ではなくimmutableなMessageで協調させたい場合に選択して使う通信設計です。
- UPD Commander Base Design は、処理順序・分岐・retry/fallback・cancel/resume・境界通信など、オーケストレーション自体が意味のある責務になる場合に選択して使うパターンです。単純な処理では普通のUPDを正当な標準形とします。
- Python の class、Protocol、Adapter、Registry、composition、Message、Commander、Messenger は、その境界を実現するための手段であり、それ自体を目的にしません。

参照元:
- https://github.com/tomiya7688/upd-design
- https://github.com/tomiya7688/upd-commander-base-design
- https://github.com/tomiya7688/part-swap-design
- https://github.com/tomiya7688/Message-Orientated-Design
- `specification/recommended-practices.md`
- `specification/implementation-quality.md`

Commander / Processing などの名称そのものを全コードへ強制するものではありません。
重要なのは、責務境界、依存方向、交換可能な閉じた呼び出し関係、読みやすいContract、検証可能性を維持することです。

---

## 1. 基本原則

- 読みやすさを短さより優先する。
- 明示的なコードを、暗黙的で技巧的なコードより優先する。
- 重複除去そのものを目的にせず、意味のある共通化を行う。
- 変更範囲は必要最小限にし、無関係なリファクタリングを混ぜない。
- 既存の公開API、設定形式、保存データ、CLI引数などを理由なく破壊しない。
- マジックナンバーや意味不明な文字列を処理本体へ散在させない。
- グローバル状態への依存を増やさない。
- import時に重い処理や外部副作用を実行しない。
- 正常系だけでなく、失敗時の挙動も設計する。
- コードで表現できる制約は、コメントだけに依存せずコードでも表現する。

## 2. 責務分離

- 1ファイル = 原則1責務。
- 1モジュール = 原則1責務。
- 1関数 = 原則1動作。
- ファイル名から説明しにくい独立処理が増えたら分割を検討する。
- 単純な処理を無理にクラス化しない。Pythonではモジュール + 関数でもよい。
- UI、入出力、画像処理、ComfyUI通信、設定管理など異なる責務を1つの巨大モジュールへ混在させない。

### 1000行を超えるファイルの責務監査

**1000行を超えるファイルは監査対象としますが、禁止しません。**

行数だけを理由に機械的に分割してはいけません。
一方で、1000行を超えた時点で「本当に1ファイル / 1モジュールの責務として維持するのが適切か」を明示的に再確認します。

監査では少なくとも次を確認します。

- 複数の独立責務が1ファイルへ混在していないか。
- UI、I/O、API通信、変換、保存、状態管理など異なる責務を抱え込んでいないか。
- 独立してテスト可能なまとまりを別moduleへ切り出せないか。
- class / function群が、互いに無関係な理由で同じファイルへ置かれていないか。
- ファイル内の一部変更が無関係な機能へ波及しやすくなっていないか。
- module分割によって依存方向を単純化できないか。
- 分割後に循環依存や過剰なmodule間通信を生むだけではないか。
- 大きさが、生成コード・巨大な静的定義・外部仕様との1対1対応など合理的理由によるものか。

監査の結果、単一責務としてまとまりがあり、分割するとかえって可読性・依存関係・保守性が悪化する場合は、1000行を超えたまま維持して構いません。

逆に、1000行未満であっても複数責務が混在している場合は分割対象になり得ます。
**1000行は品質判定そのものではなく、責務境界を見直すための監査トリガーです。**

レビューまたは実装時に1000行超のファイルを新規作成・大幅変更する場合は、分割しない理由を説明できる状態にします。

### 依存と処理の流れ

- 上位の制御処理が処理順序を決定し、下位モジュール同士の不要な横結合を避ける。
- 下位処理から別機能の内部実装を直接呼び回す構造を増やさない。
- 共通化する場合は、副作用の小さい変換・検証・データ構造・明示的な共通utilityを優先する。
- 隠れた実行経路より、呼び出し元を追えば処理順序が分かる構造を優先する。

## 3. Python基本スタイル

Pythonコードは原則として PEP 8 系の一般的なPython慣習に従います。
ただし、プロジェクト内でformatter等によって定義された形式がある場合は、その設定を優先します。

### インデントと空白

- インデントは4スペース。
- タブとスペースを混在させない。
- 行末の不要な空白を残さない。
- 演算子やカンマ周辺の空白は一般的なPython形式に従う。
- 過度に長い1行は分割する。
- formatterが導入されている場合はformatterの結果を正とする。

### 文字列

- 同一ファイル内でクォート形式を不必要に混在させない。
- 文字列補間は可読性が良い場合、原則としてf-stringを使用する。
- OSパスを手動の文字列連結で構築しない。

例:

```python
message = f"Loaded model: {model_name}"
```

## 4. 命名規則

名前から用途を推測できることを優先します。

### Python

- 変数・関数・メソッド: `snake_case`
- クラス: `PascalCase`
- 定数: `UPPER_SNAKE_CASE`
- モジュール・ファイル名: 原則 `snake_case.py`
- 内部利用を意図する名前: 必要に応じて `_leading_underscore`
- Boolean: `is_*`, `has_*`, `can_*`, `should_*`, `enable_*` など真偽が分かる名前を優先する。

### 名前の品質

避ける:

```python
a = load(x)
tmp = process(a)
data2 = save(tmp)
```

推奨:

```python
workflow = load_workflow(workflow_path)
processed_workflow = normalize_workflow(workflow)
save_workflow(processed_workflow, output_path)
```

- `data`, `info`, `obj`, `tmp`, `value` など曖昧な名前は、狭いスコープを除き多用しない。
- 略語は一般的に意味が明確なものに限定する。
- 同じ概念には同じ用語を使用する。

## 5. import規約

- 原則としてファイル先頭にimportを置く。
- 標準ライブラリ、サードパーティ、プロジェクト内importを論理的に分ける。
- wildcard import（`from x import *`）は使用しない。
- 循環importを回避するためだけの場当たり的な関数内importを増やさない。
- optional dependencyや循環参照回避など、明確な理由がある場合のみ局所importを使用する。
- 未使用importを残さない。
- 同一モジュールを複数の異なる方法でimportして可読性を下げない。

例:

```python
from pathlib import Path

import requests

from comfyui_support_tools.config import AppConfig
```

## 6. 関数

1つの関数に、取得・検証・変換・保存・描画・通知など複数の独立動作を詰め込みすぎない。

複数動作が必要な場合は小さな関数へ分割し、上位処理から順に呼び出す。

ただし、1つの責務を完了するために不可分な小処理まで機械的に分割する必要はありません。

### 引数と戻り値

- 引数が過剰に増えた場合は、責務過多またはデータ構造化不足を疑う。
- Boolean引数を多数並べて挙動を切り替えるAPIは避ける。
- 戻り値の意味が分かりにくい巨大tupleは避け、必要ならdataclass等を使用する。
- 可変オブジェクトをデフォルト引数にしない。

非推奨:

```python
def build(items=[]):
    ...
```

推奨:

```python
def build(items=None):
    if items is None:
        items = []
```

## 7. 型ヒント

- 新規の公開関数、主要な内部API、複雑なデータ構造には可能な範囲で型ヒントを付ける。
- 型ヒントは可読性向上のために使用し、必要以上に複雑な型パズルを作らない。
- `Any` は外部ライブラリ境界など必要な場所へ限定する。
- 意味のあるデータ構造には `dataclass`, `TypedDict`, `Protocol`, Enum等を必要に応じて使用する。
- `dict[str, object]` のような曖昧な構造がコード全体へ伝播しないようにする。
- `None` を取り得る値は、その可能性がコードから分かるようにする。

例:

```python
from pathlib import Path

def load_prompt(path: Path) -> str:
    return path.read_text(encoding="utf-8")
```

## 8. オブジェクト指向・モジュール独立性

このプロジェクトでは、オブジェクト指向を「クラス・継承・カプセル化を多用すること」とは定義しません。

最優先するのは、**各モジュールが独立した責務を持ち、他モジュールの内部実装へ依存せず、交換・削除・単体テストしやすい構造を維持すること**です。

カプセル化、抽象化、interface、Protocol、classなどは、その独立性を実現するための手段として使用します。

### パーツ組み換え設計を標準のcomposition原則とする

このプロジェクトでは、[パーツ組み換え設計](https://github.com/tomiya7688/part-swap-design) をUPDと組み合わせて適用します。

UPDは **「その責務をどの層へ置き、どの境界を通して処理を流すか」** を決めます。
パーツ組み換え設計は **「どこまでを1単位として、呼び出し元を変えずに内部実装を丸ごと交換できるようにするか」** を決めます。

ここでいう「パーツ」は、1つのmodule、package、Application内部のsubsystem、adapter、複数moduleをまとめた単位のいずれでも構いません。1 class = 1パーツではありません。最重要なのは **閉じた呼び出し関係** です。外部の呼び出し元はパーツの公開入口Contractだけを使い、下位の内部実装はそのパーツの中へ閉じ込めます。

#### 閉じた呼び出し関係

- パーツ外のコードは、便利だからという理由で内部helperや下位moduleを直接import / callしてはなりません。
- パーツ内部のhelperを、無関係な複数機能が直接呼ぶ事実上の共通APIへしないでください。
- 本当に複数の外部利用者が同じ責務を必要とする場合は、明示的な共通Contractを定義するか、その責務自体を独立したパーツへ昇格させます。別パーツのprivate helperを公開して済ませてはいけません。
- 同格のパーツ同士が互いの内部実装を直接呼び合う構造を避けます。処理を終えたら上位Commander / Orchestratorへ制御を返し、次のパーツ選択は上位側が行います。
- `shared` / `common` / `utils` / registryを、意図したパーツ境界を迂回する「開いた呼び出し関係」の抜け道として使ってはいけません。

#### 安定したパーツ境界

- 交換可能なパーツごとに、必要最小限の公開input / output Contractを定義します。
- 実装Aから実装Bへ差し替えるとき、通常は利用側を修正しない設計を目指します。変更してよいのはcomposition root、registry登録、設定binding、DI bindingなど、実装選択を担当する境界です。
- 交換可能な実装間では、入出力の形と意味上の保証を安定させます。Contractが許す範囲なら内部algorithmや出力品質は変わって構いません。仕様が要求しない限り、完全に同じ結果を出す必要はありません。
- パーツContractを破壊的に変更する場合は、version / migration pathを用意します。内部表現の変更を理由に、すべての利用側へ修正を波及させてはいけません。
- 利用側は、具体class名、private module path、model名、file path、private dictionary layoutではなく、semantic ID、capability、Protocol / Contract、明示的result typeへ依存します。
- 実装固有optionはtypedなpart config / bindingの後ろへ閉じます。利用側へ `if backend == ...`、`if model == ...` のような具象分岐を散在させてはいけません。
- 実装差は可能な範囲でcapability / result Contractとして公開し、上位Router / Orchestratorが解決します。

#### パーツ組み換え設計とUPDの組み合わせ

- **Application** を通常の最大責務境界とします。1つのApplicationは独立して理解できる状態を保ち、別Applicationの内部実装を直接importしてはいけません。
- Application内部では、UPDに従ってUI / Process / DataとCommander / Messenger / Processingの責務を決めます。
- その責務の中にある交換可能なalgorithm / backend / adapterを、パーツ組み換え設計の「パーツ」として扱います。
- 上位Orchestratorがパーツの選択と順序を決めます。オーケストレーション自体が十分複雑な場合だけCommanderを導入します。Commanderを使う場合、パーツの選択・順序・差し替え・retry・fallbackを指揮できますが、パーツ内部のalgorithmそのものを抱え込んではいけません。
- 非同期配送、IPC、HTTP/WebSocket、queue/event、別process/Application通信など、通信・transport自体を独立責務にしたい場合だけMessengerを導入します。単純な同一process内UPDフローへ、形式だけのMessengerを置く必要はありません。
- directory構造を埋めるためだけの空のCommander / Messenger class・fileを作ってはいけません。
- shared Contract / value objectはパーツ境界を越えて共有できます。shared implementationは、本当に共通責務である場合だけ置きます。「複数箇所から同じ内部helperを呼びたい」という理由だけでsharedへ移してはいけません。

このリポジトリで交換パーツになりやすい代表例:

- image generation backend / workflow adapter
- model family evidence detector
- evaluator / ranker / repair strategy
- frame / image filter、OCR / text detector
- trainer / personalization adapter
- video decode / analysis backend
- storage / cache / artifact / export adapter
- Post Process processor

#### パーツの粒度: 過分割しない

パーツ組み換え設計は、すべての小関数へinterfaceやregistryを作ることを要求しません。

- パーツ内部の依存関係が複雑でも、その依存が閉じた境界内に収まっているなら、複数moduleをまとめて1パーツとして扱って構いません。
- さらに細かく分割するのは、その小単位を独立して交換・テスト・所有・再利用する価値が管理コストを上回る場合です。
- 1つのownerからしか呼ばれず、単独交換の価値が低い内部algorithmはownerのパーツ内に保持して構いません。
- 「すべてを交換可能に見せる」ことを目的に、不要な抽象層・registry・interfaceを増やしてはいけません。
- 行数だけでパーツ境界を決めません。責務、呼び出し関係、交換コストで判断します。

#### Contract / swap test

明示的なextension point / 交換可能パーツには次を適用します。

- パーツ内部helperだけでなく、公開入口Contractからテストします。
- 複数の交換実装がある場合、可能な範囲で同一のcontract test suiteを実行します。
- fake / minimal implementationをテストで差し替え、利用側を変更せずに動くことを確認できる形を優先します。
- 利用側testは、具体実装自体を検証する場合を除き、具体class名、private module path、内部state layoutへ依存してはいけません。
- boundary testとは別に、実装固有の内部testを持つことは問題ありません。
- Contract上、実装ごとに結果差が許される場合は、内部動作の完全一致ではなく、必須invariant、result shape、failure semantics、Acceptanceを検証します。

### Message Orientated Designは独立した状態主体間で選択適用する

このプロジェクトでは、[Message Orientated Design](https://github.com/tomiya7688/Message-Orientated-Design) を**条件付きで採用**します。すべてのclassやfunctionをMessage通信へ変える規則ではありません。

このプロジェクトでの解釈:

- Message Orientated Designの「object」は、単なるPython classではなく、**独立した状態とlifecycleを所有する主体**とします。例: Application、service、worker、long-running job runtime、training session、plugin host等。
- 1つの主体 / 1つのPart Swap part内部では、通常のfunction callを標準とします。
- 独立主体間で、直接呼び出しや状態参照がlifecycle・ownership・concurrency・transportを密結合にする場合、Messageを使用します。
- pure helper、local validation、小さな変換、1 ownerの内部algorithmを、形式のためだけにMessage endpointへしてはいけません。

#### Message Orientated Designを使う条件

次の要素が実質的にある場合、Message境界を優先します。

- senderとreceiverが独立したmutable state / lifecycleを所有する
- async / event / queueで協調する価値がある
- process / service / Application / plugin / worker境界を越える
- progress / cancel / completion / failure / state-change通知が第一級のinteractionになる
- 同じ意味のrequest/eventを複数receiverまたは交換可能receiverが処理し得る
- requestを現在状態に応じてどう解釈するかをreceiver自身が決めるべき

このリポジトリでの代表例:

- Main GUI <-> external / subprocess service
- Job Runtime <-> worker
- Character Registry <-> training / personalization Application
- LoRA trainer <-> Training Doctor
- 長時間video / image processing worker
- direct internal importでは境界違反になるcross-Application notification

#### Message Orientated Designを使わない条件

次は通常のfunction / Contract callを維持します。

- pure / stateless helper
- 1つの閉じたPart Swap part内部
- 小さな同期validation / conversion
- caller / calleeが同じlifecycle / ownerに属するlocal algorithm
- Sender / Receptor / Managerを増やしてもcouplingが減らない場合

#### Message境界の規則

Message Orientated境界を採用した場合:

- **主体間 = Message、主体内部 = Function Call** を基本とします。
- 他主体のprivate / internal functionを直接呼びません。
- 他主体が所有する内部状態を直接読み書きしません。
- Messageは作成後immutableとします。意味・宛先・contentを変更する場合は新しいMessageを作ります。
- 選択したMessage境界を越える応答は、新しいMessageとして返します。相手主体の内部へ隠れたdirect callbackを作りません。
- repository全体へ未構造な `dict[str, object]` を流すのではなく、frozen dataclass等のtyped / explicit Message Contractを優先します。
- Message自体へglobal IDを必須にしません。request / run / job correlation IDはprotocol上必要な場合だけ持たせます。
- Senderは主体からMessageを出す境界、ReceptorはMessageを受信しtypeを識別して内部処理へdispatchする境界とします。
- Receptorへdomain validation、authorization、scoring、業務判断を抱え込ませません。それらは主体内部のProcess / Processingが担当します。
- Message Managerは**配送だけ**を担当します。global service locator、workflow engine、model router、retry policy、persistence、domain判断へ肥大化させてはいけません。
- 必要最小のmanager / domain scopeで配送します。すべてのMessageを1つのglobal event busへ強制しません。

#### UPD / Part Swap / Commanderとの関係

- UPDは、状態と意味をどの責務 / layerが所有するかを決めます。
- Part Swap Designは、receiver内部の実装をstable boundaryの後ろで交換可能にします。
- Message Orientated Designは、独立した状態主体間の通信方法を決めます。
- Commander / Orchestratorは、必要な場合にworkflowの順序を決めます。Message ManagerはCommanderの代わりではなく、CommanderもMessage配送の代わりではありません。
- UPD Messengerと、Message Orientated DesignのSender / Receptor / Message Managerは関連する通信手段ですが、自動的に同一の抽象とは扱いません。責務が本当に一致する場合だけ統合します。

#### Message Contract test

Message Orientated境界では最低限、必要に応じ次を検証します。

- Messageのimmutability / typed shape
- supported / unsupported message type
- Receptorから内部処理へのdispatch
- 配送infraにdomain処理が入っていないこと
- response / event Contract
- failure / cancellation semantics
- receiver / transportを交換してもsenderがreceiver内部へ依存しないこと

意図的に普通のin-process function callとしている処理へ、Message infrastructure testを要求しません。

### モジュールを第一の設計単位とする

- classより先にmodule / package / Applicationの責務境界を決める。
- 1つのmoduleは、自分の責務を完結して説明できる状態を目指す。
- moduleが他moduleの内部状態やprivate実装を知る必要がある設計を避ける。
- moduleの差し替え・削除で、多数の無関係なmodule修正が必要になる場合は境界を見直す。
- 単体テスト時に、無関係なmodule一式を起動しなければならない構造を避ける。
- module内部のclass構成は、外部moduleから見えなくてもよい設計を優先する。

### 依存は最小限かつ一方向にする

- 循環依存を作らない。
- AがBへ依存し、BもAへ依存する双方向依存を避ける。
- peer module同士が互いを直接呼び回す構造を避ける。
- 下位moduleが上位の具体実装へ依存しない。
- 利用側が依存先の依存先まで知る「推移的な実装知識」を持たない。
- 依存関係はimport、constructor/function引数、Contract等から追跡できる明示的な形を優先する。
- global registry、service locator、巨大singleton等で依存関係を隠さない。

基本形:

```text
Orchestrator / Commander
  ├─ Module A
  ├─ Module B
  └─ Module C
```

避ける形:

```text
Module A
  ↓
Module B
  ↓
Module C
  ↓
Module A
```

Module Aの処理後にModule Bを実行する必要がある場合、原則としてAからBを直接呼ぶのではなく、上位のOrchestrator / Commanderへ結果を返し、上位が次の処理を決定します。

### 実装ではなくContractへ依存する

module間通信が必要な場合、相手moduleの具体class・内部関数・内部データ構造へ直接依存するより、必要最小限の公開Contractへ依存します。

Contractの例:

- 小さな公開関数/API
- `Protocol`
- ABC / interface
- dataclass / TypedDict等の明示的な入出力型
- command / result object
- event / message
- callback

ただし、抽象化そのものを目的に不要なinterfaceを作りません。

**複数実装の差し替え、テストdouble、module境界の固定など、独立性に具体的な効果がある場合に抽象化します。**

Python例:

```python
from typing import Protocol


class ImageSource(Protocol):
    def load(self, image_id: str) -> bytes:
        ...


class ThumbnailGenerator:
    def __init__(self, image_source: ImageSource) -> None:
        self._image_source = image_source
```

`ThumbnailGenerator` は具体的な保存moduleを知らず、必要なContractだけを知る形を優先します。

### データ所有権を明確にする

- あるmoduleが所有する状態を、別moduleが直接書き換えない。
- mutableな共有global stateをmodule間通信に使わない。
- 「誰が更新してよいデータか」が不明な構造を避ける。
- 他moduleへ渡すデータは、必要に応じてimmutableな値、DTO、dataclass、copy等を利用する。
- 外部moduleが内部dictの特定キー構成に依存し続ける設計を避ける。
- 保存形式・API形式とmodule内部表現を分離できる場合は分離する。

### 横断処理は上位へ戻す

複数moduleへまたがる判断や処理順序は、個別moduleへ埋め込まず上位の制御層へ置きます。

例:

```text
悪い例:
ImageModule -> TagModule -> SaveModule -> UIModule

推奨:
Commander
  -> ImageModule
  <- ImageResult
  -> TagModule
  <- TagResult
  -> SaveModule
  <- SaveResult
  -> UIへ結果通知
```

各moduleは「次に何を実行するか」まで判断せず、自分の責務を完了して結果を返すことを優先します。

### 共通moduleを依存のゴミ箱にしない

- `common`, `utils`, `helpers` へ何でも集めない。
- 共通化する処理は、責務と利用範囲を説明できる単位にする。
- domain固有の判断を汎用utilityへ移さない。
- 多数のmoduleが1つの巨大common moduleへ依存する構造を避ける。
- 共通Contractと共通実装を必要に応じて分離する。

### 継承より独立性を優先する

- 継承階層によってmodule間結合が強くなる場合は継承を使わない。
- 再利用だけを理由に継承しない。
- composition、委譲、小さなProtocolを優先できる場合はそれらを検討する。
- 基底classの変更が多数の機能へ波及する巨大継承階層を作らない。
- framework都合で継承が必要な場合は、framework境界に限定することを推奨する。

### classの使用方針

- 状態、ライフサイクル、ポリモーフィズムなどclass化する理由がある場合に使用する。
- 単なるnamespace目的だけで不要なclassを作らない。
- God Objectを作らない。
- dataclassで十分な単純データは、過剰なgetter/setter classにしない。
- private相当の内部状態を外部moduleから直接操作する設計に依存しない。
- 1つのclassが複数moduleの責務を集約する構造を避ける。

### 独立性の確認基準

新規moduleまたは大きな変更では、次を確認します。

- このmoduleは単独で責務を説明できるか。
- このmoduleだけをunit testできるか。
- 他moduleのprivate実装をimportしていないか。
- 依存先は必要最小限か。
- 依存方向は一方向か。
- 循環依存がないか。
- 別実装へ交換するとき利用側の変更を局所化できるか。
- moduleを削除したとき無関係な機能まで壊れないか。
- module間で共有mutable stateを持っていないか。
- 複数moduleの処理順序を個別module自身が勝手に決めていないか。

## 9. コメントとdocstring

### コメント

- コメントはコードの逐語的な説明ではなく、処理の目的・区切り・理由を書く。
- 「何をしているか」がコードから明らかな場合、同じ内容をコメントで繰り返さない。
- 「なぜこの実装が必要か」「なぜ一見不自然な処理をしているか」を優先して残す。
- TODOを残す場合は、可能なら理由や関連Issueを併記する。
- 古くなったコメントを放置しない。

例:

```python
# ComfyUI側は未指定値と明示的なnullを別扱いするため、
# Noneのキーは送信前に除外する。
payload = remove_none_values(payload)
```

### 恒久的な宣言コメント規約: JSON-like Comment Outs

このプロジェクトでは、[Json-like-comment-outs](https://github.com/tomiya7688/Json-like-comment-outs) を**恒久的な宣言レベルのコメント規約**として採用します。

仕様解釈は同リポジトリの日本語版仕様を正本とします。

- Canonical specification: `docs/jp/SPECIFICATION.md`
- Canonical templates: `docs/jp/TEMPLATE.md`

#### 適用対象

プロジェクト管理下の新規・変更コードでは、原則として次の宣言直前に JSON-like Comment Outs を置きます。

- class
- function
- method

既存legacyコードを規約適用だけのために一括変更する必要はありません。
ただし、対象のclass / function / methodを実質的に変更した場合は、その宣言のコメントも本規約へ合わせます。

自動生成コード、vendorコード、外部由来コードなど、プロジェクト側でコメントを保守すべきでないコードは対象外です。

#### プロジェクト標準のSemantic Key

ツール解析と表記揺れ防止のため、comfyUI_support_tools では日本語キーを標準とします。

- `責務`: 対象の責務
- `処理`: 主な処理・振る舞い
- `フィールド`: classが保持する主要状態
- `引数`: 入力値
- `戻り値`: 戻り値
- `副作用`: 外部状態への変更（必要な場合）
- `エラー`: 呼び出し元が意識すべき失敗条件（必要な場合）
- `補足`: その他の重要事項（必要な場合）

同じSemantic Keyを同一ブロック内で日本語・英語の両方で重複記述しません。

#### class

classでは最低限、`責務` と `フィールド` を記述します。
主要な振る舞いがある場合は `処理` も記述します。

Python例:

```python
# {
#   責務: [
#     WorkflowRunner: ComfyUI workflowの実行状態を管理する
#   ]
#   フィールド: [
#     client: ComfyUIとの通信クライアント
#     active_prompt_id: 現在実行中のprompt ID
#   ]
#   処理: [
#     1: workflowを送信する
#     2: 実行状態を追跡する
#   ]
# }
class WorkflowRunner:
    ...
```

#### function / method

function / methodでは最低限、`責務`、`処理`、`引数`、`戻り値` を記述します。

- `処理` は原則として実際の処理順に並べる。
- 処理番号は `1` からの連番を使用する。
- `責務` には宣言名を含める。
- `引数` の名前は実装上の引数名と対応させる。
- 戻り値がない場合も `戻り値: []` として明示してよい。

Python例:

```python
# {
#   責務: [
#     load_workflow: workflow JSONを読み込む
#   ]
#   処理: [
#     1: 入力パスを検証する
#     2: JSONファイルを読み込む
#     3: workflow構造を返す
#   ]
#   引数: [
#     path: 読み込むworkflowファイルのパス
#   ]
#   戻り値: [
#     workflow: 読み込んだworkflowデータ
#   ]
#   エラー: [
#     OSError: ファイルを読み込めない場合
#   ]
# }
def load_workflow(path: Path) -> dict[str, object]:
    ...
```

#### 実装内部のコメント

JSON-like Comment Outs は宣言レベルの構造化コメント用です。
関数内部の条件分岐、処理理由、ローカル変数などには通常の `#` コメントを使用します。

```python
# キャッシュに存在しない場合だけComfyUIへ問い合わせる
if cached_result is None:
    result = fetch_result(prompt_id)
```

内部コメントまでJSON-like形式にする必要はありません。

#### docstringとの関係

JSON-like Comment Outs は、Pythonのdocstringや外部ツールが要求する公式ドキュメント形式を禁止しません。

- 宣言の責務・処理・入出力を人間 / AI / 解析ツールが読むための標準: JSON-like Comment Outs
- Python runtimeや既存ツールがdocstringを必要とする場合: docstringを併用してよい

同じ情報を機械的に二重記述しすぎないようにします。

#### 保守

- コメント内容は実装と一致させる。
- 責務、処理、フィールド、引数、戻り値の意味が変わった場合は同じ変更でコメントも更新する。
- 空テンプレートを一時的に生成することは許容するが、完成コードでは必要項目を埋める。
- 有効なJSONである必要はない。Json-like-comment-outsの構文・Semantic Keyの考え方を優先する。
- コメント形式だけを守るために可読性を悪化させない。

### docstring

次のような対象にはdocstringを付けることを推奨します。

- 公開モジュール
- 公開クラス
- 公開関数
- 複雑な内部関数
- 副作用や例外条件が分かりにくい処理

docstringには必要に応じて以下を記述します。

- 目的
- 引数の意味
- 戻り値
- 主な例外
- 副作用
- 利用上の注意

型情報を型ヒントとdocstringへ二重記述しすぎないようにします。

## 10. 例外処理

- `except Exception:` や裸の `except:` で無条件に問題を握りつぶさない。
- 捕捉できる具体的な例外を可能な範囲で指定する。
- 復旧できない例外は、不必要に捕捉して成功扱いにしない。
- 例外を別の例外へ変換する場合は原因を保持する。
- エラーメッセージには、失敗した対象や操作が分かる情報を含める。
- ユーザー向けメッセージと開発者向け詳細ログを必要に応じて分離する。
- `print` してから例外を無視するだけの処理を標準パターンにしない。

例:

```python
try:
    config = load_config(config_path)
except OSError as exc:
    raise ConfigLoadError(f"Failed to load config: {config_path}") from exc
```

---

## 11. ログ

- ライブラリ・アプリ本体の診断情報には原則としてloggingを使用する。
- 一時的なデバッグ用`print()`をコミットへ残さない。
- ログレベルを用途に応じて使い分ける。
  - DEBUG: 開発・詳細診断
  - INFO: 通常動作の主要イベント
  - WARNING: 継続可能だが注意が必要
  - ERROR: 処理失敗
- 同じエラーを複数層で重複ログしすぎない。
- パスワード、APIキー、Cookie、認証トークン等をログへ出力しない。
- 大量の画像データ、base64、巨大JSON等を通常ログへそのまま出さない。

---

## 12. ファイル・パス・エンコーディング

- Pythonのパス操作は原則として `pathlib.Path` を優先する。
- パス区切り文字を手動で結合しない。
- Windows固有パスをコードへハードコードしない。
- テキストファイルのエンコーディングは原則として明示する。
- 一時ファイルは `tempfile` 等の安全な仕組みを使用する。
- ファイル上書き時は、重要データ破損の可能性を考慮する。
- ユーザー指定パスを扱う場合、意図しないディレクトリ削除・上書きへ注意する。

例:

```python
from pathlib import Path

config_path = Path(config_dir) / "config.json"
text = config_path.read_text(encoding="utf-8")
```

---

## 13. 設定値・定数

- マジックナンバー、モデル名、タイムアウト値、固定パス等を処理本体へ散在させない。
- 意味のある定数名を付けるか、設定へ切り出す。
- ユーザーが変更すべき値と、内部実装定数を区別する。
- 同じ既定値を複数箇所で独立定義しない。
- 環境依存値はコードへ直接埋め込まない。

---

## 14. データ構造

- キー文字列へ強く依存する巨大dictを無制限に広げない。
- 構造が安定しているデータはdataclass、TypedDict、Enum等を検討する。
- 外部APIから受け取ったデータは境界で検証・正規化してから内部処理へ渡す。
- 内部表現と外部API形式を必要に応じて分離する。
- 関数間で同じdictを暗黙に破壊的変更し続ける設計を避ける。

---

## 15. 外部API・ComfyUI通信

- HTTP/APIアクセスと純粋なデータ変換を分離する。
- タイムアウトなしのネットワークアクセスを避ける。
- 通信失敗、タイムアウト、不正レスポンスを考慮する。
- APIレスポンスを無条件に正しい形式と仮定しない。
- リトライする場合は、無限リトライにしない。
- 再実行すると危険な操作では、安易な自動リトライをしない。
- ComfyUIのworkflow/prompt形式をUIコードから直接組み立て続けず、変換層へ分離することを推奨する。

---

## 16. subprocess・外部コマンド

- 可能な限り `shell=True` を使用しない。
- 外部入力をそのままシェルコマンドへ連結しない。
- 引数は文字列結合ではなくリストで渡す。
- return codeを確認する。
- stdout/stderrを必要に応じて記録する。
- タイムアウト可能な処理ではタイムアウトを検討する。
- 実行ファイルの存在や依存条件を事前確認できる場合は確認する。

例:

```python
subprocess.run(
    ["ffmpeg", "-i", str(input_path), str(output_path)],
    check=True,
)
```

## 17. セキュリティ

このリポジトリはローカルツール中心であっても、外部入力を信頼しすぎないこと。

- APIキー、パスワード、秘密鍵、トークンをソースへコミットしない。
- 認証情報をログへ出さない。
- `eval()` / `exec()` を外部入力へ使用しない。
- pickle等、任意コード実行につながり得る形式を信頼できない入力へ使用しない。
- ZIP展開時のpath traversal等、ファイル展開先に注意する。
- ユーザー入力をsubprocessやSQL等へ直接文字列連結しない。
- 外部から取得したモデル・スクリプト・pluginを自動実行する処理では信頼境界を明確にする。

---

## 18. 依存ライブラリ

- 標準ライブラリで十分な処理のためだけに大型依存を追加しない。
- 新規依存を追加する場合は、利用目的を明確にする。
- 既に同等機能の依存が存在する場合は重複導入を避ける。
- optionalな機能のためにアプリ全体の必須依存を不必要に増やさない。
- import名とpackage名が異なる場合など、導入方法を必要に応じてREADME等へ記載する。
- 未使用になった依存は削除を検討する。

---

## 19. 性能

- 可読性を犠牲にした早すぎる最適化をしない。
- 重い画像処理、動画処理、モデルロード等では明らかな不要コピーや重複ロードを避ける。
- 大容量ファイルを必要なく一括でメモリへ読み込まない。
- キャッシュは無効化条件とライフサイクルを明確にする。
- 最適化が必要な場合は可能な範囲で計測結果に基づく。
- GPU/VRAM資源を扱う処理は、解放タイミングや重複ロードを意識する。

---

## 20. 並行処理・非同期処理

- thread、process、asyncioを必要性なく混在させない。
- UIスレッドを長時間ブロックする処理を避ける。
- 共有可変状態を最小化する。
- キャンセル、タイムアウト、終了処理を考慮する。
- background workerの例外を握りつぶさない。
- GUI更新をworker threadから直接行って問題になるframeworkでは、適切なUIスレッドへ戻す。
- 並行実行で同じファイルや設定を更新する可能性がある場合、競合を考慮する。

---

## 21. UIコード

- UI生成、イベント配線、ビジネスロジックを可能な限り分離する。
- 長時間処理をUIイベントハンドラ内へ直接詰め込まない。
- 入力検証はUIだけに依存せず、処理層でも必要な条件を保証する。
- エラーメッセージはユーザーが次の行動を判断できる内容にする。
- UI部品から直接ファイル、API、ComfyUI内部へ深くアクセスする構造を増やさない。
- UIから分離可能な処理はGUIなしでテストできるようにする。

---

## 22. 後方互換性

既存利用者の環境やworkflowを壊さないことを重視します。

変更時は必要に応じて以下を確認します。

- 既存CLI引数
- 設定ファイル形式
- 保存データ形式
- ComfyUI workflow形式
- 公開関数/API
- ファイル配置
- Windows向け起動スクリプト
- 既存モデル・custom nodeとの連携

破壊的変更が必要な場合は、移行方法または互換層を検討します。

---

## 23. テスト

- 既存テストを壊さない。
- 仕様変更時は必要に応じてテストも同時に更新する。
- 新規の重要処理には可能な範囲でテストを追加する。
- bug fixでは、可能であれば再発防止テストを追加する。
- UIから分離可能なロジックは、GUIを起動せずテストできる構造を優先する。
- 外部APIやComfyUIサーバーを必要としない純粋ロジックはunit test可能な形にする。
- テスト間で実行順序へ依存しない。
- テストが実ユーザーデータを破壊しないようにする。
- 一時ファイル・一時ディレクトリを利用する。

---

## 24. 実装品質

変更を完了扱いにする前に、対象範囲で利用可能な以下を通過させます。

- Python構文チェック / importチェック
- formatter または format check
- linter
- unit test
- 必要な起動・ビルド確認
- GitHub Actions等の既存CI

既存テストやCIを壊した状態を通常の完了状態としません。

警告・lint違反を意図的に残す場合は、対象範囲を最小化し、理由を設定またはコメントへ残します。

### 自動化ツール

formatter / linter / type checker等が導入されている場合、そのプロジェクト設定を正とします。

未導入のツールを各開発者・AIが勝手に必須化してはいけません。
新しい品質ツールを標準化する場合は、設定ファイル・CI・ドキュメントを合わせて導入します。

既存構造との互換性が必要な場合を除き、補助スクリプトをリポジトリ直下へ増やさないことを推奨します。

## 26. レビュー観点

コードレビューでは少なくとも以下を確認します。

- 名前だけで役割を理解しやすいか。
- 1ファイルに複数の独立責務が混在していないか。
- 1000行を超えるファイルについて、責務分割の要否を監査したか。
- 1関数に複数の独立動作が詰め込まれていないか。
- GUI / API / データ処理 / 永続化が不必要に密結合していないか。
- 下位モジュール同士の横結合が増えていないか。
- 処理の入口と依存方向が追いやすいか。
- import時の副作用が増えていないか。
- 例外を握りつぶしていないか。
- ログへ秘密情報を出していないか。
- パスや外部入力を安全に扱っているか。
- 不要な依存を追加していないか。
- 公開APIや既存設定を理由なく破壊していないか。
- コメントがコードの言い換えではなく意図を説明しているか。
- formatter / lint / test / CIを無効化して問題を隠していないか。
- 新規処理に必要なテストがあるか。

## 27. 適用方針

新規コードは原則として本規約へ従います。

既存コードは、無関係な変更で一括リファクタリングせず、触った範囲から段階的に適用します。

性能・互換性・外部API仕様などの理由で規約から外れる必要がある場合は、実装上の合理的理由を優先します。
その場合は可能な限り理由をコードまたは文書へ残してください。

「規約に合わせるためだけ」の大規模変更より、動作を壊さず継続的に改善することを優先します。

## 28. 新規ApplicationのUPD + パーツ組み換え標準

新規の主要Applicationは、UPD責務境界について `doc/architecture/upd_standard.md` に従い、
交換可能な実装境界について本規約8章のパーツ組み換え設計に従います。
`src/comfyui_support_tools/applications/` 配下で Application単位 + UI / Process / Data に分離します。

### 標準形: 普通のUPD

単純なApplicationでは普通のUPDを標準とします。

- UIは外部入力・出力・表示責務を持つ。
- Processはアプリケーション判断・検証・変換・domain flowを持つ。
- Dataは保存・取得・外部data accessを持つ。
- UIからProcessを飛び越えてDataへ直接依存しない。
- 別Applicationの内部moduleへ直接依存しない。
- 単純な同一process内処理では、隣接layer間を小さな明示Contract / functionで接続してよい。directoryを埋めるためだけのCommander / Messengerを作らない。

### オーケストレーションが責務になったらCommanderを使う

次のような要素が実質的に存在する場合、Commander / Orchestratorを導入します。

- 複数の独立パーツを順番に実行する
- routing / branchingで次のパーツを選ぶ
- retry / fallback / Top-K / repair / 再評価でflowが変化する
- long jobのcancel / pause / resume / checkpointが処理順へ影響する
- workflow自体をパーツと独立して重点テストする必要がある

Commanderを使う場合、呼び出し順序とflow判断だけを担当します。algorithm、I/O、inference、保存処理は適切なProcessing / partへ置きます。

### 通信が責務になったらMessengerを使う

次のように通信/transport自体を分離する価値がある場合、Messenger / transport境界を導入します。

- 非同期 / event / queue配送
- IPC / subprocess service通信
- HTTP / WebSocket等のremote API
- 明示的な別process / 別Application通信
- protocol変換やreliabilityを独立してテストしたい場合

Messengerを使う場合、Contractを運ぶだけにし、domain処理を持たせません。

### パーツ組み換え要件

- Application内部の交換可能なbackend / algorithm / adapterは閉じたpart Contractを持ち、consumerから内部moduleを直接importしない。
- 実装差し替え時の変更は原則としてcomposition root、registry / config binding、またはpart内部へ閉じ、無関係なconsumerへ波及させない。
- 明示的なextension pointには可能な範囲でcontract / swap testを用意する。
- interface・Commander・Messengerを作るためだけに、1 ownerの内部処理を過分割しない。
- legacy `scripts/` は一括移行せず、触った責務から段階移行する。

architecture checkerは責務/境界違反を検出するために使用し、単純なflowへ空のCommander / Messenger scaffoldを強制してはいけません。現行checkerがこの規約より厳しい場合は、本規約を正本としてchecker側を更新し、不要な構造をコードへ強制しません。

## 29. 文書・READMEの日本語 / 英語併記

README とプロジェクト所有の文書は、日本語・英語の両方を維持します。

- 新規文書は日英両方を同時に作成する。
- 既存文書を実質的に変更する場合は、対応する他言語版も同じPRで更新する。
- 日英で仕様・要件・警告の意味を変えない。
- 別ファイル方式の場合は文書冒頭に相互リンクを置く。
- 片言語のみの既存legacy文書は、無関係な変更で一括翻訳せず、触った文書から段階的にペア化する。
- 自動生成物、第三者原文、ライセンス原文など正本性が重要なものは翻訳必須対象から除外できる。
- 翻訳に自信がない専門用語は、意味を推測して変更せず原語を併記する。
- 片方の言語だけ更新して完了扱いにしない。

## 継承の共通規約（必須・レビュー基準）

### 禁止：具象クラス起点の連続継承

- **具象クラス A を継承するクラス B を、クラス C がさらに継承してはならない。** すなわち `具象 A → B → C` を禁止する。中間の B が具象か抽象かは問わない。
- **`抽象 A → 具象 B → C` は、この禁止規則の違反ではない。** ただし設計・可読性のレビューは必要とする。
- この規則単独では `具象 A → B` の一段の継承を一律には禁止しない。ただし、既存の「具象クラスの継承そのものを禁止」など、より厳しいプロジェクト規則を常に優先する。
- 言語に暗黙で存在する `Object` / `System.Object` / `java.lang.Object` 等の最上位基底型、インターフェースの継承・実装はこの違反判定の対象外とする。

### 継承を選ぶ前の設計原則

- **具体的な処理を持つクラスの継承は原則として避ける。** 抽象クラスであっても具体的な実装を持つなら同じ。継承関係そのものに意味がなく、処理の再利用だけが目的なら委譲・合成を優先する。
- 基底型と派生型に共通する意味のある形・契約が実際に存在する、または同じ形の型が今後必要になると合理的に予想できる場合に限って継承を検討する。抽象化・継承階層を「いつか使うかもしれない」というだけで作らない。
- 形式上許可される継承でも、階層が読みづらい、責務の理解が難しい、変更の波及が過大、置換可能性が成立しない等の問題があれば**レビューで不合格**とする。「禁止規則に抵触しない」は設計の承認を意味しない。

### 適用範囲と例外

- 当該プロジェクトが意図的にその継承構造を採用し、設計正本に理由・適用範囲を明記している箇所は例外とする。単に既存コードに同じ形があることを例外の根拠にしない。
- コンパイラ・解析器が入力として扱う言語の継承仕様、サンプル、検証用fixtureと、プロジェクト自身の実装規約を区別する。
- 新規・変更するプロジェクト所有コードへ適用し、無関係な既存コードの一斉書き換えを要求しない。
