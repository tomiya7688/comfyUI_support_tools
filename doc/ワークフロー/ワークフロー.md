# 1回分の開発ワークフロー

1回の作業は、1つのGitHub Issueに対して、開始から検証・記録までを完了させる。

## 開始時

1. 作業ツリーを確認する。ユーザーの未追跡・未コミット変更は保持し、対象外のファイルを変更しない。
2. **リモートの変更を取り込む。** `git fetch origin` の後、現在の作業ブランチへ `git pull --ff-only origin main` を実行する。競合が発生した場合は勝手に解決せず、作業を止めて報告する。
3. GitHubの未完了Issueと優先度を確認する。
4. 対象Issueの本文、コメント、受け入れ条件を読む。必要なら `python scripts/context_packet.py <issue番号>` で作業パケットを生成する。
5. `doc/Agent.md` と対象ディレクトリの局所ルールを確認する。巨大な変更履歴や無関係な資料は読み込まない。

## 実装

6. Issueの受け入れ条件から、今回の作業範囲を小さく確定する。範囲外の改善やリファクタリングを混ぜない。
7. 作業ブランチを作成する。
8. 実装する。既存のユーザー変更、設定、生成物を削除・上書きしない。
9. 必要なテストを追加または更新する。

## 検証と記録

10. 対象テスト、構文チェック、`git diff --check` を実行する。
11. GUI・外部API・GPU・実バックエンドなど未実行のものは、実行済みと推測で補わず未検証として記録する。
12. 必要な設計書、`doc/ver.md`、`doc/Agent.md`、クラス責務表を更新する。完了済み項目を開発予定へ重複して残さない。
13. 変更ファイル、検証コマンド、結果、未検証事項をIssueへコメントする。

## GitHub反映

14. 対象ファイルだけをステージし、意味のある単位でコミットする。
15. ブランチをリモートへプッシュし、必要ならプルリクエストを作成する。
16. レビュー・CI・受け入れ条件を確認し、完了したIssueだけをクローズする。
17. 次の作業へ進む前に、作業ツリーとリモートの状態を再確認する。

## 定期作業

- クラス責務表を更新する。
- Issueの重複・古い記述・未完了チェック項目を整理する。
- 評価チームからの指摘は、該当Issueへ追記または新規Issue化する。
