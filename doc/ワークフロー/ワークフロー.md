# 1回分の開発ワークフロー

[English](workflow.md) | [文書索引](../README.md)

1回の作業は1つのIssue、または既存の関連PRに限定する。設計・実装・レビューを別の責務として扱い、兼務しても各段階の記録を分ける。正本はIssueの要件、ソースコード、[コーディング規約](../コーディング規約.md)、この手順書である。作業メモやAI要約は正本ではない。

## 共通の開始手順（毎回）

1. `git remote -v`、`git status --short --branch` で対象リポジトリとユーザーの変更を確認する。未追跡・未コミットのデータを保護する。
2. **次の行動を決める前に必ず `git fetch origin` を実行する。** 失敗した場合はリモートの新しさを未確認と記録し、古い状態に依存する選定・マージを進めない。取得と統合は別操作である。
3. 取得後、`git log --oneline --left-right HEAD...origin/main` と関連ファイルの差分を必要な範囲で確認する。作業ブランチで無条件に `git pull origin main` しない。ベース更新は変更・競合を見て、適切なブランチ上で明示的に行う。
4. オープンPRを先に調べる。今回のIssueに関係するPRがあれば、その最新head、差分、CI、レビュー指摘、競合を確認し、重複PRを作らず既存PRの修正・レビューを優先する。無関係なPRの全件精読はしない。
5. 該当PRがなければIssueを1つ選ぶ。番号指定があればそれを優先し、なければ `python tools/context/select_task.py` を使う。Issueの本文・関連コメント・優先度・依存関係・受け入れ条件を読む。必要に応じて `python tools/context/task_packet.py <Issue番号>` を使う。

この手順は新しい作業回、継続再開、PRレビュー、マージ判断のたびに繰り返す。「前回取得した」は代用にならない。取得できない場合は、確認済みのローカル作業とリモート依存の判断を分けて報告する。

## 共通責務と個別責務

全担当者の共通責務は、Issueの範囲と一次情報を確認すること、ユーザーデータを保護すること、関係ない変更を混ぜないこと、検証済みと未検証を分けること、日英の文書を同期すること、引き継ぎを残すこと。単独担当でも省略しない。

| 役割 | 個別の成果と判断 | 次への引き継ぎ |
| --- | --- | --- |
| 調整担当 | PR先行確認、Issueの優先度・依存関係と担当の整理、重複防止。権限のない代理送信やマージはしない。 | Issue/PR、担当者、base/head、次の担当 |
| 設計担当 | 目的・対象外・境界・代替案・受け入れ条件・検証方法を定める。実装完了やレビュー承認は主張しない。 | 設計判断、参照元、未解決点、実装可能な最小単位 |
| 実装担当 | 専用ブランチで変更・テスト・文書を作成し、自己レビューとPRを用意する。自己レビューを独立レビューと呼ばない。 | 変更範囲、検証結果、未検証、リスク、PR URL |
| レビュー担当 | 最新headの差分を独立に確認し、根拠と場所を付けて指摘し、修正後は新headを再確認する。 | 指摘と解決状態、残る検証、判定したhead |
| マージ担当 | 必須CI、レビュー、競合、base/head、`pr_safety` を最終確認する。失敗・不明ならマージしない。 | マージ結果、Issue状態、残課題 |

兼務は可能だが、どの役割を誰が担い、独立レビューが実施されたかをIssue/PRに明示する。独立レビュアーがいなければ「自己レビューのみ」と記録する。権限がない操作は実施したことにせず依頼として引き継ぐ。

引き継ぎにはIssue/PR、担当役割・次担当、ブランチ/base/head、作業範囲、根拠へのリンク、実行した検証と結果、未検証事項、未解決の指摘、次の一手を記載する。永続的な判断はIssue/PRまたは正本の文書へ残す。

## 設計

Issueから Goal / Required / Acceptance と対象外を抽出する。既存の設計・コード・対応テストを検索で絞り、必要箇所だけ読む。変更の責務、API/依存境界、外部コードのライセンス、GUI/API/GPU等の実機検証要否を決める。大きい仕事は依存順の小単位に分け、1PRに混ぜない。判断に必要な証拠がそろったら調査を止める。

## 実装

`main`/`master` を直接編集せず、Issue専用ブランチを使う。変更前に[コーディング規約](../コーディング規約.md)を読む。対象コードと対応テストを編集し、日英の関連文書を同じPRで更新する。ユーザーの未追跡データをステージしない。静的検査・対象テスト・`git diff --check` を実行し、GUI操作、外部API、GPU、実バックエンド、CIは実行できたものだけを明記する。

PR前に、受け入れ条件、差分範囲、JSON-like宣言コメント、エラー処理、依存/ライセンス、テストの意味、日英の文書、秘密情報やユーザーデータの混入を自己レビューする。`python tools/completion/completion_gate.py` が通らなければコミット/PRへ進まない。対象ファイルだけを明示ステージし、PR本文は日本語でIssue・変更点・検証結果・未検証/保留を記載する。

## レビューと完了

レビュー担当は最新リモートとPRの最新headを取得し、Issueの受け入れ条件と差分を照合する。要求漏れ、予期しないファイル、規約違反、回帰、セキュリティ/秘密情報、外部コードのライセンス、日英文書、テスト不足を確認する。指摘はファイル/箇所・影響・再現/根拠を示す。修正が入れば同じPRの新headで再レビューし、古いheadのCI成功を流用しない。

マージ担当は最新headで必須CIと未解決レビューを確認し、`python tools/completion/pr_safety.py <PR番号>` を実行する。競合、不明なマージ可否、失敗した必須チェック、予期しない差分、リポジトリ/base/head不一致なら止める。安全に完了したPRだけをマージし、Issueと残課題を更新する。次の作業回も必ずリモート取得から始める。

## コンテキスト削減

[AI Context Reducer](https://github.com/tomiya7688/ai-context-reducer) の「目録→作業パケット→必要箇所のみ→探索停止」を採用する。入口文書は所在と責務だけを示し、長い仕様を複製しない。検索 (`rg --files`、`rg -n`) で対象を絞り、Issue・コード・テスト・差分という一次情報へ進む。作業パケットは目的、範囲、制約、受け入れ条件、参照リンクを短く保持する一時メモとし、正本を置き換えない。新情報や矛盾・テスト失敗が出た場合だけ調査を広げる。
