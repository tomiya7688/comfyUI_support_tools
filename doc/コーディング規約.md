# コーディング規約

本規約は comfyUI_support_tools 全体で使用する一般コーディング規約です。

設計・責務分離については `upd-commander-base-design` の考え方を基礎としつつ、Pythonプロジェクトとして一般的な可読性、保守性、テスト容易性、安全性、互換性の規約も含めます。

参照元:
- https://github.com/tomiya7688/upd-commander-base-design
- `specification/recommended-practices.md`
- `specification/implementation-quality.md`

Commander / Processing などの名称そのものを全コードへ強制するものではありません。
重要なのは、責務境界、依存方向、可読性、検証可能性を維持することです。

---

## 1. 基本原則

- 読みやすさを短さより優先する。
- 明示的なコードを、暗黙的で技巧的なコードより優先する。
- 重複除去そのものを目的にせず、意味のある共通化を行う。
- 変更範囲は必要最小限にし、無関係なリファクタリングを混ぜない。
- 既存の公開API、設定形式、保存データ、CLI引数などを理由なく破壊しない。
- マジックナンバーや意味不明な文字列を処理本体へ散在させない。
- グローバル状態への依存を増やさない。
- import時に重い処理や外部副作用を実行しない。
- 正常系だけでなく、失敗時の挙動も設計する。
- コードで表現できる制約は、コメントだけに依存せずコードでも表現する。

---

## 2. 責務分離

- 1ファイル = 原則1責務。
- 1モジュール = 原則1責務。
- 1関数 = 原則1動作。
- ファイル名から説明しにくい独立処理が増えたら分割を検討する。
- 単純な処理を無理にクラス化しない。Pythonではモジュール + 関数でもよい。
- UI、入出力、画像処理、ComfyUI通信、設定管理など異なる責務を1つの巨大モジュールへ混在させない。

### 依存と処理の流れ

- 上位の制御処理が処理順序を決定し、下位モジュール同士の不要な横結合を避ける。
- 下位処理から別機能の内部実装を直接呼び回す構造を増やさない。
- 共通化する場合は、副作用の小さい変換・検証・データ構造・明示的な共通utilityを優先する。
- 隠れた実行経路より、呼び出し元を追えば処理順序が分かる構造を優先する。

---

## 3. Python基本スタイル

Pythonコードは原則として PEP 8 系の一般的なPython慣習に従います。
ただし、プロジェクト内でformatter等によって定義された形式がある場合は、その設定を優先します。

### インデントと空白

- インデントは4スペース。
- タブとスペースを混在させない。
- 行末の不要な空白を残さない。
- 演算子やカンマ周辺の空白は一般的なPython形式に従う。
- 過度に長い1行は分割する。
- formatterが導入されている場合はformatterの結果を正とする。

### 文字列

- 同一ファイル内でクォート形式を不必要に混在させない。
- 文字列補間は可読性が良い場合、原則としてf-stringを使用する。
- OSパスを手動の文字列連結で構築しない。

例:

```python
message = f"Loaded model: {model_name}"
```

---

## 4. 命名規則

名前から用途を推測できることを優先します。

### Python

- 変数・関数・メソッド: `snake_case`
- クラス: `PascalCase`
- 定数: `UPPER_SNAKE_CASE`
- モジュール・ファイル名: 原則 `snake_case.py`
- 内部利用を意図する名前: 必要に応じて `_leading_underscore`
- Boolean: `is_*`, `has_*`, `can_*`, `should_*`, `enable_*` など真偽が分かる名前を優先する。

### 名前の品質

避ける:

```python
a = load(x)
tmp = process(a)
data2 = save(tmp)
```

推奨:

```python
workflow = load_workflow(workflow_path)
processed_workflow = normalize_workflow(workflow)
save_workflow(processed_workflow, output_path)
```

- `data`, `info`, `obj`, `tmp`, `value` など曖昧な名前は、狭いスコープを除き多用しない。
- 略語は一般的に意味が明確なものに限定する。
- 同じ概念には同じ用語を使用する。

---

## 5. import規約

- 原則としてファイル先頭にimportを置く。
- 標準ライブラリ、サードパーティ、プロジェクト内importを論理的に分ける。
- wildcard import（`from x import *`）は使用しない。
- 循環importを回避するためだけの場当たり的な関数内importを増やさない。
- optional dependencyや循環参照回避など、明確な理由がある場合のみ局所importを使用する。
- 未使用importを残さない。
- 同一モジュールを複数の異なる方法でimportして可読性を下げない。

例:

```python
from pathlib import Path

import requests

from comfyui_support_tools.config import AppConfig
```

---

## 6. 関数

1つの関数に、取得・検証・変換・保存・描画・通知など複数の独立動作を詰め込みすぎない。

複数動作が必要な場合は小さな関数へ分割し、上位処理から順に呼び出す。

ただし、1つの責務を完了するために不可分な小処理まで機械的に分割する必要はありません。

### 引数と戻り値

- 引数が過剰に増えた場合は、責務過多またはデータ構造化不足を疑う。
- Boolean引数を多数並べて挙動を切り替えるAPIは避ける。
- 戻り値の意味が分かりにくい巨大tupleは避け、必要ならdataclass等を使用する。
- 可変オブジェクトをデフォルト引数にしない。

非推奨:

```python
def build(items=[]):
    ...
```

推奨:

```python
def build(items=None):
    if items is None:
        items = []
```

---

## 7. 型ヒント

- 新規の公開関数、主要な内部API、複雑なデータ構造には可能な範囲で型ヒントを付ける。
- 型ヒントは可読性向上のために使用し、必要以上に複雑な型パズルを作らない。
- `Any` は外部ライブラリ境界など必要な場所へ限定する。
- 意味のあるデータ構造には `dataclass`, `TypedDict`, `Protocol`, Enum等を必要に応じて使用する。
- `dict[str, object]` のような曖昧な構造がコード全体へ伝播しないようにする。
- `None` を取り得る値は、その可能性がコードから分かるようにする。

例:

```python
from pathlib import Path

def load_prompt(path: Path) -> str:
    return path.read_text(encoding="utf-8")
```

---

## 8. クラス

- 状態、ライフサイクル、ポリモーフィズムなどクラス化する理由がある場合に使用する。
- 単なる名前空間目的だけで不要なクラスを作らない。
- God Objectを作らない。
- 継承より合成を優先できる場合は合成を検討する。
- private相当の内部状態を外部から直接書き換えることへ依存しない。
- dataclassで十分な単純データは、過剰なgetter/setterクラスにしない。

---

## 9. コメントとdocstring

### コメント

- コメントはコードの逐語的な説明ではなく、処理の目的・区切り・理由を書く。
- 「何をしているか」がコードから明らかな場合、同じ内容をコメントで繰り返さない。
- 「なぜこの実装が必要か」「なぜ一見不自然な処理をしているか」を優先して残す。
- TODOを残す場合は、可能なら理由や関連Issueを併記する。
- 古くなったコメントを放置しない。

例:

```python
# ComfyUI側は未指定値と明示的なnullを別扱いするため、
# Noneのキーは送信前に除外する。
payload = remove_none_values(payload)
```

### 恒久的な宣言コメント規約: JSON-like Comment Outs

このプロジェクトでは、[Json-like-comment-outs](https://github.com/tomiya7688/Json-like-comment-outs) を**恒久的な宣言レベルのコメント規約**として採用します。

仕様解釈は同リポジトリの日本語版仕様を正本とします。

- Canonical specification: `docs/jp/SPECIFICATION.md`
- Canonical templates: `docs/jp/TEMPLATE.md`

#### 適用対象

プロジェクト管理下の新規・変更コードでは、原則として次の宣言直前に JSON-like Comment Outs を置きます。

- class
- function
- method

既存legacyコードを規約適用だけのために一括変更する必要はありません。
ただし、対象のclass / function / methodを実質的に変更した場合は、その宣言のコメントも本規約へ合わせます。

自動生成コード、vendorコード、外部由来コードなど、プロジェクト側でコメントを保守すべきでないコードは対象外です。

#### プロジェクト標準のSemantic Key

ツール解析と表記揺れ防止のため、comfyUI_support_tools では日本語キーを標準とします。

- `責務`: 対象の責務
- `処理`: 主な処理・振る舞い
- `フィールド`: classが保持する主要状態
- `引数`: 入力値
- `戻り値`: 戻り値
- `副作用`: 外部状態への変更（必要な場合）
- `エラー`: 呼び出し元が意識すべき失敗条件（必要な場合）
- `補足`: その他の重要事項（必要な場合）

同じSemantic Keyを同一ブロック内で日本語・英語の両方で重複記述しません。

#### class

classでは最低限、`責務` と `フィールド` を記述します。
主要な振る舞いがある場合は `処理` も記述します。

Python例:

```python
# {
#   責務: [
#     WorkflowRunner: ComfyUI workflowの実行状態を管理する
#   ]
#   フィールド: [
#     client: ComfyUIとの通信クライアント
#     active_prompt_id: 現在実行中のprompt ID
#   ]
#   処理: [
#     1: workflowを送信する
#     2: 実行状態を追跡する
#   ]
# }
class WorkflowRunner:
    ...
```

#### function / method

function / methodでは最低限、`責務`、`処理`、`引数`、`戻り値` を記述します。

- `処理` は原則として実際の処理順に並べる。
- 処理番号は `1` からの連番を使用する。
- `責務` には宣言名を含める。
- `引数` の名前は実装上の引数名と対応させる。
- 戻り値がない場合も `戻り値: []` として明示してよい。

Python例:

```python
# {
#   責務: [
#     load_workflow: workflow JSONを読み込む
#   ]
#   処理: [
#     1: 入力パスを検証する
#     2: JSONファイルを読み込む
#     3: workflow構造を返す
#   ]
#   引数: [
#     path: 読み込むworkflowファイルのパス
#   ]
#   戻り値: [
#     workflow: 読み込んだworkflowデータ
#   ]
#   エラー: [
#     OSError: ファイルを読み込めない場合
#   ]
# }
def load_workflow(path: Path) -> dict[str, object]:
    ...
```

#### 実装内部のコメント

JSON-like Comment Outs は宣言レベルの構造化コメント用です。
関数内部の条件分岐、処理理由、ローカル変数などには通常の `#` コメントを使用します。

```python
# キャッシュに存在しない場合だけComfyUIへ問い合わせる
if cached_result is None:
    result = fetch_result(prompt_id)
```

内部コメントまでJSON-like形式にする必要はありません。

#### docstringとの関係

JSON-like Comment Outs は、Pythonのdocstringや外部ツールが要求する公式ドキュメント形式を禁止しません。

- 宣言の責務・処理・入出力を人間 / AI / 解析ツールが読むための標準: JSON-like Comment Outs
- Python runtimeや既存ツールがdocstringを必要とする場合: docstringを併用してよい

同じ情報を機械的に二重記述しすぎないようにします。

#### 保守

- コメント内容は実装と一致させる。
- 責務、処理、フィールド、引数、戻り値の意味が変わった場合は同じ変更でコメントも更新する。
- 空テンプレートを一時的に生成することは許容するが、完成コードでは必要項目を埋める。
- 有効なJSONである必要はない。Json-like-comment-outsの構文・Semantic Keyの考え方を優先する。
- コメント形式だけを守るために可読性を悪化させない。

### docstring

次のような対象にはdocstringを付けることを推奨します。

- 公開モジュール
- 公開クラス
- 公開関数
- 複雑な内部関数
- 副作用や例外条件が分かりにくい処理

docstringには必要に応じて以下を記述します。

- 目的
- 引数の意味
- 戻り値
- 主な例外
- 副作用
- 利用上の注意

型情報を型ヒントとdocstringへ二重記述しすぎないようにします。

## 10. 例外処理

- `except Exception:` や裸の `except:` で無条件に問題を握りつぶさない。
- 捕捉できる具体的な例外を可能な範囲で指定する。
- 復旧できない例外は、不必要に捕捉して成功扱いにしない。
- 例外を別の例外へ変換する場合は原因を保持する。
- エラーメッセージには、失敗した対象や操作が分かる情報を含める。
- ユーザー向けメッセージと開発者向け詳細ログを必要に応じて分離する。
- `print` してから例外を無視するだけの処理を標準パターンにしない。

例:

```python
try:
    config = load_config(config_path)
except OSError as exc:
    raise ConfigLoadError(f"Failed to load config: {config_path}") from exc
```

---

## 11. ログ

- ライブラリ・アプリ本体の診断情報には原則としてloggingを使用する。
- 一時的なデバッグ用`print()`をコミットへ残さない。
- ログレベルを用途に応じて使い分ける。
  - DEBUG: 開発・詳細診断
  - INFO: 通常動作の主要イベント
  - WARNING: 継続可能だが注意が必要
  - ERROR: 処理失敗
- 同じエラーを複数層で重複ログしすぎない。
- パスワード、APIキー、Cookie、認証トークン等をログへ出力しない。
- 大量の画像データ、base64、巨大JSON等を通常ログへそのまま出さない。

---

## 12. ファイル・パス・エンコーディング

- Pythonのパス操作は原則として `pathlib.Path` を優先する。
- パス区切り文字を手動で結合しない。
- Windows固有パスをコードへハードコードしない。
- テキストファイルのエンコーディングは原則として明示する。
- 一時ファイルは `tempfile` 等の安全な仕組みを使用する。
- ファイル上書き時は、重要データ破損の可能性を考慮する。
- ユーザー指定パスを扱う場合、意図しないディレクトリ削除・上書きへ注意する。

例:

```python
from pathlib import Path

config_path = Path(config_dir) / "config.json"
text = config_path.read_text(encoding="utf-8")
```

---

## 13. 設定値・定数

- マジックナンバー、モデル名、タイムアウト値、固定パス等を処理本体へ散在させない。
- 意味のある定数名を付けるか、設定へ切り出す。
- ユーザーが変更すべき値と、内部実装定数を区別する。
- 同じ既定値を複数箇所で独立定義しない。
- 環境依存値はコードへ直接埋め込まない。

---

## 14. データ構造

- キー文字列へ強く依存する巨大dictを無制限に広げない。
- 構造が安定しているデータはdataclass、TypedDict、Enum等を検討する。
- 外部APIから受け取ったデータは境界で検証・正規化してから内部処理へ渡す。
- 内部表現と外部API形式を必要に応じて分離する。
- 関数間で同じdictを暗黙に破壊的変更し続ける設計を避ける。

---

## 15. 外部API・ComfyUI通信

- HTTP/APIアクセスと純粋なデータ変換を分離する。
- タイムアウトなしのネットワークアクセスを避ける。
- 通信失敗、タイムアウト、不正レスポンスを考慮する。
- APIレスポンスを無条件に正しい形式と仮定しない。
- リトライする場合は、無限リトライにしない。
- 再実行すると危険な操作では、安易な自動リトライをしない。
- ComfyUIのworkflow/prompt形式をUIコードから直接組み立て続けず、変換層へ分離することを推奨する。

---

## 16. subprocess・外部コマンド

- 可能な限り `shell=True` を使用しない。
- 外部入力をそのままシェルコマンドへ連結しない。
- 引数は文字列結合ではなくリストで渡す。
- return codeを確認する。
- stdout/stderrを必要に応じて記録する。
- タイムアウト可能な処理ではタイムアウトを検討する。
- 実行ファイルの存在や依存条件を事前確認できる場合は確認する。

例:

```python
subprocess.run(
    ["ffmpeg", "-i", str(input_path), str(output_path)],
    check=True,
)
```

---

## 17. セキュリティ

このリポジトリはローカルツール中心であっても、外部入力を信頼しすぎないこと。

- APIキー、パスワード、秘密鍵、トークンをソースへコミットしない。
- 認証情報をログへ出さない。
- `eval()` / `exec()` を外部入力へ使用しない。
- pickle等、任意コード実行につながり得る形式を信頼できない入力へ使用しない。
- ZIP展開時のpath traversal等、ファイル展開先に注意する。
- ユーザー入力をsubprocessやSQL等へ直接文字列連結しない。
- 外部から取得したモデル・スクリプト・pluginを自動実行する処理では信頼境界を明確にする。

---

## 18. 依存ライブラリ

- 標準ライブラリで十分な処理のためだけに大型依存を追加しない。
- 新規依存を追加する場合は、利用目的を明確にする。
- 既に同等機能の依存が存在する場合は重複導入を避ける。
- optionalな機能のためにアプリ全体の必須依存を不必要に増やさない。
- import名とpackage名が異なる場合など、導入方法を必要に応じてREADME等へ記載する。
- 未使用になった依存は削除を検討する。

---

## 19. 性能

- 可読性を犠牲にした早すぎる最適化をしない。
- 重い画像処理、動画処理、モデルロード等では明らかな不要コピーや重複ロードを避ける。
- 大容量ファイルを必要なく一括でメモリへ読み込まない。
- キャッシュは無効化条件とライフサイクルを明確にする。
- 最適化が必要な場合は可能な範囲で計測結果に基づく。
- GPU/VRAM資源を扱う処理は、解放タイミングや重複ロードを意識する。

---

## 20. 並行処理・非同期処理

- thread、process、asyncioを必要性なく混在させない。
- UIスレッドを長時間ブロックする処理を避ける。
- 共有可変状態を最小化する。
- キャンセル、タイムアウト、終了処理を考慮する。
- background workerの例外を握りつぶさない。
- GUI更新をworker threadから直接行って問題になるframeworkでは、適切なUIスレッドへ戻す。
- 並行実行で同じファイルや設定を更新する可能性がある場合、競合を考慮する。

---

## 21. UIコード

- UI生成、イベント配線、ビジネスロジックを可能な限り分離する。
- 長時間処理をUIイベントハンドラ内へ直接詰め込まない。
- 入力検証はUIだけに依存せず、処理層でも必要な条件を保証する。
- エラーメッセージはユーザーが次の行動を判断できる内容にする。
- UI部品から直接ファイル、API、ComfyUI内部へ深くアクセスする構造を増やさない。
- UIから分離可能な処理はGUIなしでテストできるようにする。

---

## 22. 後方互換性

既存利用者の環境やworkflowを壊さないことを重視します。

変更時は必要に応じて以下を確認します。

- 既存CLI引数
- 設定ファイル形式
- 保存データ形式
- ComfyUI workflow形式
- 公開関数/API
- ファイル配置
- Windows向け起動スクリプト
- 既存モデル・custom nodeとの連携

破壊的変更が必要な場合は、移行方法または互換層を検討します。

---

## 23. テスト

- 既存テストを壊さない。
- 仕様変更時は必要に応じてテストも同時に更新する。
- 新規の重要処理には可能な範囲でテストを追加する。
- bug fixでは、可能であれば再発防止テストを追加する。
- UIから分離可能なロジックは、GUIを起動せずテストできる構造を優先する。
- 外部APIやComfyUIサーバーを必要としない純粋ロジックはunit test可能な形にする。
- テスト間で実行順序へ依存しない。
- テストが実ユーザーデータを破壊しないようにする。
- 一時ファイル・一時ディレクトリを利用する。

---

## 24. 実装品質

変更を完了扱いにする前に、対象範囲で利用可能な以下を通過させます。

- Python構文チェック / importチェック
- formatter または format check
- linter
- unit test
- 必要な起動・ビルド確認
- GitHub Actions等の既存CI

既存テストやCIを壊した状態を通常の完了状態としません。

警告・lint違反を意図的に残す場合は、対象範囲を最小化し、理由を設定またはコメントへ残します。

### 自動化ツール

formatter / linter / type checker等が導入されている場合、そのプロジェクト設定を正とします。

未導入のツールを各開発者・AIが勝手に必須化してはいけません。
新しい品質ツールを標準化する場合は、設定ファイル・CI・ドキュメントを合わせて導入します。

---

## 25. ツール・スクリプト配置

開発補助ツールは原則として `tools/` 配下へ配置します。

```text
tools/
└─ <tool_name>/
   ├─ script/
   │  └─ ...
   ├─ README.md
   └─ ...
```

既存構造との互換性が必要な場合を除き、補助スクリプトをリポジトリ直下へ増やさないことを推奨します。

## 26. レビュー観点

コードレビューでは少なくとも以下を確認します。

- 名前だけで役割を理解しやすいか。
- 1ファイルに複数の独立責務が混在していないか。
- 1関数に複数の独立動作が詰め込まれていないか。
- GUI / API / データ処理 / 永続化が不必要に密結合していないか。
- 下位モジュール同士の横結合が増えていないか。
- 処理の入口と依存方向が追いやすいか。
- import時の副作用が増えていないか。
- 例外を握りつぶしていないか。
- ログへ秘密情報を出していないか。
- パスや外部入力を安全に扱っているか。
- 不要な依存を追加していないか。
- 公開APIや既存設定を理由なく破壊していないか。
- コメントがコードの言い換えではなく意図を説明しているか。
- formatter / lint / test / CIを無効化して問題を隠していないか。
- 新規処理に必要なテストがあるか。

---

## 27. 適用方針

新規コードは原則として本規約へ従います。

既存コードは、無関係な変更で一括リファクタリングせず、触った範囲から段階的に適用します。

性能・互換性・外部API仕様などの理由で規約から外れる必要がある場合は、実装上の合理的理由を優先します。
その場合は可能な限り理由をコードまたは文書へ残してください。

「規約に合わせるためだけ」の大規模変更より、動作を壊さず継続的に改善することを優先します。

## 28. 新規ApplicationのUPD標準

新規の主要Applicationは `doc/architecture/upd_standard.md` に従い、
`src/comfyui_support_tools/applications/` 配下で Application単位 + UI / Process / Data に分離します。

- Commanderは呼び出しの指揮のみを担当する。
- Messengerはlayer間通信のみを担当する。
- Processingへ実処理を置く。
- UIからDataへ直接依存しない。
- 別Applicationの内部moduleへ直接依存しない。
- Application間は明示API/Contractで通信する。
- legacy `scripts/` は一括移行せず、触った責務から段階移行する。

新規Application領域は `tools/architecture/upd_check.py` をstrictに通過する必要があります。
